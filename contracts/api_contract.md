# Контракт API: роли и права доступа

Версия: 0.2.0 (черновик на проверку тимлиду)
Базовый префикс: `/api/v1`

Машиночитаемый контракт со всеми новыми эндпоинтами:
[`openapi.roles.json`](./openapi.roles.json).

`openapi.current.json` — зафиксированный контракт фронтенда (20 путей).
Он сознательно не перегенерирован: в репозитории нет Node.js, поэтому
`frontend/src/shared/api/schema.d.ts` и счётчики в
`frontend/scripts/check-api.mjs` не обновлены. После принятия контракта
нужно выполнить `npm run api:generate` и обновить проверку.

## 1. Роли

В таблице `users` шесть допустимых значений поля `role`:

| Роль | Назначение |
| --- | --- |
| `user` | Обычный пользователь: личный кабинет, регистрация себя и близких, оплата, анкета |
| `typist` | Наборщик: ввод бумажных анкет, сопоставление анкеты и карты |
| `registrar` | Регистратор на старте: поиск и просмотр анкет, выдача карты |
| `marker` | Маркер: сканирование карт только на назначенных КП и финише |
| `organizer` | Организатор: статистика, списки, роли (кроме admin), назначение КП маркерам |
| `admin` | Администратор: всё, включая аккаунты организаторов и системные настройки |

`participant` **не является ролью**. Участник мероприятия — это строка в
таблице `participants`, принадлежащая пользователю (`users`). Один
пользователь может иметь несколько участников (семья, прошлые годы).
Значение `participant` в `users.role` больше не используется; при старте
приложения существующие записи автоматически переводятся в `user`
(мягкая миграция в `create_db`).

Валидация значения:

* CHECK-констрейнт `ck_users_role` в таблице `users` (для новых БД);
* Pydantic-тип `Role` во всех запросах и ответах (422 при неверном значении);
* `require_role(...)` проверяет роль на каждом защищённом эндпоинте.

## 2. Матрица доступа

Обозначения: `—` нет доступа (401 без токена / 403 с токеном),
`owner` — только владелец записи, `assigned` — только назначенный КП.

### Публичные и общие

| Метод | Путь | Доступ | Что делает |
| --- | --- | --- | --- |
| POST | `/auth/register` | публично | Создаёт аккаунт с ролью `user` |
| POST | `/auth/login` | публично | Выдаёт JWT и текущую роль |
| GET | `/auth/me` | любой авторизованный | Свой профиль и роль |
| GET | `/routes` | публично | Каталог маршрутов |
| GET | `/checkpoints?route_id=` | публично | КП маршрута |

### Пользователь (`user`, а также любой сотрудник как владелец данных)

| Метод | Путь | Доступ | Что делает |
| --- | --- | --- | --- |
| POST | `/participants/register` | любой авторизованный | Регистрирует себя и близких |
| GET | `/participants/my` | любой авторизованный | Только свои записи участников |
| POST | `/participants/{id}/pay` | owner | Оплата своей записи |
| GET | `/participants/{id}/passes` | owner, admin | Свои отметки прохождения КП |
| POST | `/scans/self` | любой авторизованный, owner | Отметка на КП по общему QR; только своя запись |

`/scans/self` принимает `checkpoint_barcode` и необязательные `participant_id`
или `form_id`. Если на маршруте у аккаунта несколько участников, без
уточнения возвращается 400: нельзя случайно отметить не того человека.
Сканировать чужую карту через этот эндпоинт невозможно: выборка всегда
ограничена `user_id = current_user.id`.

### Наборщик (`typist`)

| Метод | Путь | Доступ | Что делает |
| --- | --- | --- | --- |
| POST | `/typist/paper-form` | typist, admin | Вводит бумажную анкету |
| POST | `/typist/match` | typist, admin | Связывает `form_id` и `barcode` карты |
| GET | `/typist/unlinked` | typist, admin | Список непривязанных карт |

### Регистратор (`registrar`)

Только чтение. Регистратор не меняет данные и не видит статистику.

| Метод | Путь | Доступ | Что делает |
| --- | --- | --- | --- |
| GET | `/registrar/forms?query=&route_id=&limit=` | registrar, admin | Поиск анкет по номеру, ФИО, телефону, email |
| GET | `/registrar/forms/{form_id}` | registrar, admin | Анкета по номеру, данные маршрута и карты |

### Маркер (`marker`)

| Метод | Путь | Доступ | Что делает |
| --- | --- | --- | --- |
| GET | `/marker/assignments` | marker, admin | Свои назначенные КП и маршруты |
| POST | `/scans` | marker, admin; assigned | Одиночное сканирование |
| POST | `/scans/batch` | marker, admin; assigned | Массовое чтение |
| POST | `/scans/upload-file` | marker, admin; assigned | Загрузка txt-файла со штрих-кодами |

Если КП не назначен маркеру, возвращается 403. Назначения хранятся в
таблице `marker_assignments` (`user_id`, `checkpoint_id`, уникальная пара).
Маркер не видит общую статистику, чужие назначения и не меняет маршруты.

### Организатор (`organizer`)

| Метод | Путь | Доступ | Что делает |
| --- | --- | --- | --- |
| GET | `/users?role=&search=&limit=&offset=` | organizer, admin | Список аккаунтов (организатор не видит admin) |
| GET | `/users/roles` | organizer, admin | Роли, доступные для назначения |
| PATCH | `/users/{id}/role` | organizer, admin | Назначение/изменение роли |
| GET | `/organizer/stats?route_id=` | organizer, admin | Зарегистрированы, оплатили, стартовали, финишировали, на маршруте; по маршрутам и КП |
| GET | `/organizer/participants?route_id=&payment_status=&has_started=&has_finished=&search=&limit=&offset=` | organizer, admin | Списки участников |
| GET | `/organizer/markers` | organizer, admin | Маркеры и число назначенных КП |
| GET | `/organizer/markers/{id}/assignments` | organizer, admin | Назначения маркера |
| PUT | `/organizer/markers/{id}/assignments` | organizer, admin | Полная замена набора КП маркера |

Тело `PUT /organizer/markers/{id}/assignments`:

```json
{ "checkpoint_ids": [12, 13, 14] }
```

Пользователь должен уже иметь роль `marker`, иначе 400. Несуществующие КП
возвращают 404 со списком отсутствующих ID. Пустой список снимает все
назначения. Маршрут доступен маркеру через назначенные КП; отдельного
поля `route_id` нет, чтобы нельзя было выдать доступ к КП, которые
организатор не выбирал.

### Администратор (`admin`)

Администратор имеет доступ ко всем эндпоинтам организатора и
дополнительно:

| Метод | Путь | Доступ | Что делает |
| --- | --- | --- | --- |
| POST | `/admin/routes` | admin | Создать маршрут |
| PUT | `/admin/routes/{id}` | admin | Изменить маршрут |
| DELETE | `/admin/routes/{id}` | admin | Удалить/архивировать маршрут |
| POST | `/routes/{id}/map` | admin | Загрузить карту маршрута |
| POST | `/admin/checkpoints` | admin | Создать КП |
| PUT | `/admin/checkpoints/{id}` | admin | Изменить КП |
| DELETE | `/admin/checkpoints/{id}` | admin | Удалить КП |
| POST | `/admin/checkpoints/batch` | admin | Массовое создание КП |
| POST | `/admin/maps` | admin | Создать карту |
| POST | `/admin/maps/batch` | admin | Массово создать карты |
| GET | `/admin/maps/{barcode}` | admin | Информация о карте |
| PATCH | `/users/{id}/status` | admin | Блокировка/разблокировка аккаунта |
| PATCH | `/users/{id}/role` | admin | Любая роль, включая admin |

Отдельное окно админки реализуется на фронтенде; API одно и то же.
Организатор не видит администраторов в `/users` и получает 403 при
попытке изменить аккаунт администратора.

## 3. Правила назначения ролей

`PATCH /users/{id}/role`

```json
{ "role": "marker" }
```

| Правило | Результат |
| --- | --- |
| Организатор назначает `user`, `typist`, `registrar`, `marker`, `organizer` | 200 |
| Организатор назначает или снимает `admin` | 403 |
| Организатор меняет роль администратора | 403 |
| Администратор назначает любую роль | 200 |
| Смена собственной роли (если в системе остаётся другой активный admin) | 200 |
| Снять роль с последнего активного администратора | 409 |
| Неизвестная роль в теле | 422 |
| Пользователь не найден | 404 |

`PATCH /users/{id}/status`

```json
{ "is_active": false }
```

Только admin. Нельзя заблокировать последнего активного администратора
(409). Заблокированный аккаунт получает 401 на всех защищённых
эндпоинтах.

## 4. Коды ответов

| Код | Когда |
| --- | --- |
| 200/201 | Успех |
| 400 | Некорректная бизнес-операция (например, несколько участников в self-scan) |
| 401 | Нет токена, токен неверный, аккаунт заблокирован |
| 403 | Роль не даёт доступа, чужой объект, КП не назначен |
| 404 | Объект не найден (в т.ч. чужая запись участника — не раскрываем существование) |
| 409 | Попытка убрать последнего администратора |
| 422 | Ошибка схемы запроса, неизвестная роль |

## 5. Изменения схемы БД

1. `users.role`: базовое значение `user`, CHECK-констрейнт на шесть ролей.
2. `participants.user_id`: стал `NULL` — бумажная анкета может не иметь
   аккаунта (раньше использовался несуществующий `user_id = 0`).
3. Новая таблица `marker_assignments`:
   * `id` — PK;
   * `user_id` — FK на `users.id`, NOT NULL, индекс;
   * `checkpoint_id` — FK на `checkpoints.id`, NOT NULL, индекс;
   * `UNIQUE (user_id, checkpoint_id)`.
4. Мягкая миграция при старте: `role NOT IN (...)` и `role IS NULL`
   переводятся в `user`. Отдельных Alembic-ревизий в проекте пока нет.

## 6. Что осталось за рамками

* Регистратор по ТЗ «ничего не меняет», поэтому выдача карты в системе
  остаётся операцией наборщика (`/typist/match`); регистратор только
  находит анкету и видит `barcode` карты.
* Публичная регистрация всегда создаёт `user`; повышение роли — только
  через организатора/администратора.
* Почтовый сервер, PDF-анкеты, платежный шлюз и мобильное приложение —
  отдельные задачи, здесь только заглушки/существующее поведение.
