# Майская прогулка 2026 — цифровая платформа (фронтенд)

Статический клиент цифровой платформы «Майской прогулки 2026»: HTML, CSS и JavaScript без сборки. Фронтенд интегрирован с REST API бэкенда (`/api/v1`), использует JWT-авторизацию и шесть ролей.

Бэкенд запускается отдельно. Для станции наборщика предусмотрен локальный шлюз с моделью OCR.

***Чеклист готовности В конце файла!***


## Быстрый запуск

Из отдельной копии backend проекта (`main` `798bf7b`) с подготовленной синтетической SQLite и тестовыми аккаунтами запустите FastAPI. Команды PowerShell для готового backend-окружения:

```powershell
$env:PYTHONPATH = (Join-Path (Get-Location) 'src')
.venv/Scripts/python.exe -c 'from mayprogulka.database.database import engine; engine.echo=False; import uvicorn; uvicorn.run("mayprogulka.entrypoint:app", host="127.0.0.1", port=8000, access_log=False)'
```

Из корня HTML worktree в другом окне PowerShell:

```powershell
uv venv --python 3.12 .venv-ocr && uv pip sync --python .venv-ocr/Scripts/python.exe ocr_system/requirements.txt
.venv-ocr/Scripts/python.exe -m ocr_system.gateway
```

Если окружение OCR уже готово, подставьте путь к его Python 3.12 во второй команде. Откройте `http://127.0.0.1:8080/`. Главная, лендинг, маршруты, вход и рабочие экраны используют этот origin. Штаб безопасности остаётся демонстрационным макетом. `?api=` и `mp_api_base` игнорируются. Обычный статический сервер не обеспечивает API и не входит в этот сценарий запуска. Шлюз и backend рассчитаны на loopback и синтетические данные, не открывайте эти порты в сеть.

### Камера и HTTPS

Для доступа к камере на мобильных устройствах браузеры требуют HTTPS или `localhost`. При открытии по локальному IP через HTTP используется резервный путь: выбор файла через `<input type="file">`.

`index.html` — точка входа-хаб. Рабочий вход в систему — через `login.html`; после входа пользователь попадает на домашний экран своей роли.

### Публичный контур

**`index.html`** — статическая витрина: карточки контуров, быстрые ссылки на лендинг, кабинет, служебные терминалы и штаб безопасности. Авторизация не требуется.

**`mayprogulka_festival.html`** — официальный лендинг мероприятия. Таймер до старта, обзор дистанций 10 / 17 / 33 / 50 км, визуальный блок со значком финишёра, расписание и правила. Бэкенд не используется.

**`route_selector.html`** — интерактивный выбор маршрута: карточки дистанций, контрольные пункты, профиль высот, таблица сравнения и кнопка скачивания GPX. GPX формируется на клиенте как демонстрационный трек; реальные данные маршрутов с сервера не загружаются.

### Личный кабинет

**`login.html`** — вход и регистрация. Проверяет текущую сессию через `GET /api/v1/auth/me`, выполняет `POST /api/v1/auth/login` и `POST /api/v1/auth/register`, сохраняет токен и пользователя в `localStorage`, затем перенаправляет по роли:

| Роль | Домашний экран |
| :--- | :--- |
| `user` | `user_cabinet.html` |
| `typist` | `typist_station.html` |
| `registrar` | `registrar_terminal.html` |
| `marker` | `marker_terminal.html` |
| `organizer` | `control_panel.html` |
| `admin` | `control_panel.html` |

**`user_cabinet.html`** — кабинет участника:

- регистрация себя и нескольких членов семьи или группы;
- корзина участников и оплата взноса за каждого отдельно (эмуляция СБП или банковской карты с сохранением факта оплаты через API);
- именные QR-билеты и Form ID;
- карточки участников, маршрут, статус оплаты и старта, пройденная дистанция, диплом финишёра.

Используемые запросы: `GET /api/v1/participants/my`, `POST /api/v1/participants/register`, `POST /api/v1/participants/{id}/pay`, `GET /api/v1/routes`.

### Служебный контур

**`registrar_terminal.html`** — стартовый терминал регистратора. Камера-first сценарий:

- поиск анкеты по Form ID, ФИО, телефону или email (`GET /api/v1/registrar/search`);
- отображение данных участника и статуса оплаты (`GET /api/v1/registrar/forms/{form_id}`);
- приём оплаты на старте (`POST /api/v1/participants/{id}/pay`);
- выдача карты и фиксация старта (`POST /api/v1/registrar/issue-card`, идемпотентно);
- привязка карты к анкете через `POST /api/v1/typist/match`;
- просмотр несвязанных анкет (`GET /api/v1/typist/unlinked`);
- сканирование QR и штрихкодов камерой, ручной ввод кода, витрина образцов карт через `?open=cards`.

Горячие клавиши и промо-блоки со страницы убраны. Привязка карт вынесена в сворачиваемую шторку. Кнопка тестового скана показывается только в демо-режиме.

**`typist_station.html`** — станция оцифровки бумажных анкет. Две вкладки:

1. **Набор анкеты** — ручной ввод ФИО, даты рождения, пола, телефона и email, выбор маршрута, сохранение через `POST /api/v1/typist/paper-form`. Сверху расположен OCR-помощник.
2. **Сопоставление карт** — связывание анкеты и стикера карты через `POST /api/v1/typist/match`, список несвязанных карт через `GET /api/v1/typist/unlinked`.

Горячие клавиши: F1 — набор анкеты, F2 — сопоставление.

**`marker_terminal.html`** — терминал маркёра на контрольном пункте. Камера QR/CODE128, снимок и ручной ввод используют общий журнал IndexedDB. Отметка привязана к проверенному аккаунту и исходному КП. Код карты сохраняется с исходным регистром и временем приёма. Номер анкеты `PYYYY-…` для отметки не принимается.

- **В очереди** — браузер завершил локальную запись. Без сети приём доступен в уже подтверждённой сессии для последнего проверенного назначения. Открытие или перезагрузка без проверки входа блокируется. Бумажный процесс остаётся обязательным.
- **Отправляется** — перед запросом записан состав пачки. Перед отправкой терминал повторно проверяет вход и назначения. Записи с удалённым КП остаются в журнале для сверки. Пачки содержат до 50 отметок. Web Locks исключает параллельную отправку одного аккаунта в этом браузере. При отсутствии Web Locks отправка блокируется, журнал можно выгрузить.
- **Подтверждено сервером** — ответ учёл каждую отметку, результат записан в журнал. Счётчики «Новых» и «Уже были» относятся к пачке. Успех по отдельной строке не показывает, была запись создана сейчас или существовала ранее.
- **Нужна сверка / Исход неизвестен** — запись сохранена. После сбоя связи, некорректного ответа или перезагрузки во время запроса неоднозначные записи автоматически не повторяются. Повторное сканирование того же точного кода на том же КП не создаёт новую запись. Для неизвестных и отклонённых записей повторной отправки из терминала нет.

**Сверка с организатором.** Нажмите «Экспорт журнала». JSON текущего аккаунта содержит исходный КП/маршрут, точный код, время, идентификаторы и итоги попыток. Выгрузка ничего не подтверждает и не удаляет. Передайте файл по согласованному каналу. Организатор сверяет КП, код и время с фактическим реестром и бумажной картой до любых исправлений. У маркёра нет отдельного API подтверждения результата для конкретной записи. Старые `mp_marker_queue` и `mp_marker_cp` оставлены на исходном устройстве без привязки к аккаунту и скрыты из рабочего журнала. Для их восстановления организатор проверяет происхождение данных и сверяет владельца, КП и отметки по бумажным данным и реестру. Терминал не отправляет эти данные автоматически, даже под администратором.

Журнал сохраняет все состояния до предела в 5000 отметок на аккаунт. При достижении лимита, сбое хранилища или обнаружении повреждений выгрузите доступные записи и обратитесь к организатору. Не очищайте данные сайта до сверки. Защита от удаления или вытеснения данных браузером, потери устройства и доступа владельца устройства не гарантируется. Перед заменой backend/БД на том же origin выгрузите и сверяйте старые данные отдельно — числовые ID могут обозначать другие аккаунты и КП. Сервер не принимает ключ идемпотентности, поэтому терминал не гарантирует exactly-once между устройствами или фиксированный порядок на сервере. Кнопка SOS остаётся демонстрационной.

**`safety_dashboard.html`** — демонстрационный макет штаба безопасности: состояние КП, риск опоздания до заката, задержки на переходах, карточки участников, действия диспетчера и выгрузка CSV. Живого подключения к Safety Engine нет: эндпоинт `GET /api/v1/safety/alerts` в бэкенде отсутствует, данные и сценарии зашиты в страницу.

### Центр управления

**`control_panel.html`** — рабочее место организатора и администратора. Вкладки:

- **Статистика** — сводка по маршрутам, оплатам, стартам, финишам и отметкам на КП (`GET /api/v1/organizer/stats`);
- **Участники** — список с фильтрами и постраничным выводом (`GET /api/v1/organizer/participants`);
- **Маркёры и КП** — список маркёров и назначение контрольных пунктов (`GET /api/v1/organizer/markers`, `PUT /api/v1/organizer/markers/{id}/assignments`, `GET /api/v1/marker/checkpoints`);
- **Пользователи** — роли и блокировка (`GET /api/v1/admin/users`, `PATCH /api/v1/admin/users/{id}/role`, `PATCH /api/v1/admin/users/{id}/status`; блокировка доступна только администратору);
- **Система** — только для `admin`: CRUD маршрутов и КП, генерация карт, поиск карты по баркоду, управление пользователями.

Системная вкладка скрыта от организатора. Удаление выполняется подтверждением вторым нажатием, без блокирующих `confirm()`.

## Роли

Роль `participant` не существует. Участник мероприятия — это запись в таблице `participants`, принадлежащая пользователю с ролью `user`.

| Роль | Назначение |
| :--- | :--- |
| `user` | Регистрирует себя и близких, оплачивает, получает QR-билеты |
| `typist` | Оцифровывает бумажные анкеты и связывает их с картами |
| `registrar` | Принимает оплату на старте и выдаёт карты |
| `marker` | Сканирует карты на КП и финише |
| `organizer` | Смотрит статистику, участников и назначает маркёров |
| `admin` | Управляет маршрутами, КП, картами и пользователями |

Роли назначает администратор или организатор. Организатор не может выдать роль `admin` и управлять администраторами. Подробные критерии — в `ROLES.md`.

Текущее ограничение: страница наборщика открыта ролям `typist` и `admin`, хотя в навигаторе она отображается и организатору. Матрицу доступа стоит согласовать отдельно.

## OCR бумажных анкет

Поддерживается тестовый бланк Юли `FORM-MP-2026-AI-OCR-v3` с четырьмя видимыми ArUco-метками. Принимаются JPEG/PNG до 10 МБ и 24 Мп. Шлюз проверяет активную роль наборщика или администратора через `/api/v1/auth/me`. Фото обрабатывается в памяти одного локального процесса.

1. Выберите фото с камеры или из галереи. Модель предлагает ФИО, дату рождения, телефон и email. Янтарная рамка отмечает подставленные поля. Исходный результат и причины пропуска доступны рядом с фото.
2. Сверьте и исправьте поля. Пол и маршрут выберите вручную. При недоступном OCR или неподходящем бланке заполните анкету вручную.
3. Подтвердите сверку и сохраните. QR анкеты появляется после проверенного ответа бэкенда. При неизвестном исходе попросите уполномоченного сотрудника проверить реестр. Сопоставление карты выполняется отдельно.

Веса PP-OCRv6 Medium и словарь взяты из ревизии `32e701fcd2c57946779a5812744c66fb60a413c9`. SHA-1 Git blob весов — `c16362f57fc242a30a8fc51bbc29e75237a0b91c`. Проверено на Python 3.12.16. Версии зависимостей зафиксированы в `ocr_system/requirements.txt`. Проверка модели на синтетике:

```powershell
.venv-ocr/Scripts/python.exe -m unittest -v ocr_system.test_core
```

Если меняются классы оформления, локальные стили всех страниц пересобираются из корня:


## Интеграция с бэкендом

`openapi.current.json` — единственный источник истины по контрактам API. Файл `BACKEND_INTEGRATION.md` устарел и не используется.

### Авторизация

- JWT передаётся в заголовке `Authorization: Bearer <token>`.
- Токен хранится в `localStorage` под ключом `mp_auth_token`. Рабочая страница проверяет данные пользователя через `/auth/me` при открытии.
- `requireAuth()` проверяет сессию и роль через `GET /api/v1/auth/me` и общую матрицу доступа в `api_config.js`.
- Для продакшена нужен HTTPS: долгоживущий JWT в `localStorage` — компромисс для демонстрации.

### Особенности контрактов

- Ошибки валидации пакетной отправки могут приходить внутри HTTP 200 в массиве `errors[]`.
- `DELETE` обычно возвращает `204` без тела.
- Удаление используемого маршрута возвращает `204`, но фактически не удаляет маршрут; интерфейс показывает предупреждение.
- Повторный `PUT /api/v1/typist/paper-form/{id}` для уже созданной анкеты возвращает `409`.
- `GET /api/v1/registrar/search` ищет без учёта регистра, а `POST /api/v1/scans/batch` и `POST /api/v1/typist/match` — с учётом. Клиент не должен приводить баркоды к верхнему регистру.
- `GET /api/v1/admin/users/roles` возвращает массив объектов `{ value, title }`.


## Что осталось

### Требует решения бэкенд-команды

1. **SOS и Safety Engine.** Эндпоинты безопасности не реализованы. Кнопка SOS маркёра показывает заглушку, `safety_dashboard.html` работает на демо-данных. Нужно либо реализовать `/api/v1/safety/alerts` и отправку тревог, либо убрать эти экраны из демонстрации.
2. **Идемпотентность бумажной анкеты.** Повторное сохранение уже созданной анкеты даёт `409`. Нужно решить, должен ли `PUT` обновлять запись или клиент обязан отслеживать создание.
3. **Регистр баркодов.** Привести поиск, сканирование и сопоставление к единому регистронезависимому поведению.
4. **Удаление используемого маршрута.** Сейчас сервер отвечает `204`, но ничего не удаляет. Корректнее вернуть `409` с причиной.
5. **Массовый импорт КП.** Эндпоинт `POST /api/v1/admin/checkpoints/batch` готов, но интерфейса загрузки CSV в центре управления пока нет.
6. **Импорт GPX/KML.** Скачивание GPX на `route_selector.html` — демонстрационное. Для реального импорта нужно сопоставление путевых точек маршрута с контрольными пунктами.

### Фронтенд-бэклог

1. CSV-импорт контрольных пунктов в системной вкладке центра управления.
2. Импорт треков GPX/KML и привязка путевых точек к КП.
3. Согласование матрицы доступа: организатор и страница наборщика.
4. Финальная приёмка по чеклисту `AI_AGENT_TASK.md`.
5. Чистка тестовых данных, тестовых карт и демонстрационных записей перед показом.
6. Шрифты загружаются с Google Fonts. Для полной автономности можно отдельно подготовить локальные шрифты.
7. Косметика: тост `MPToast` появляется сверху по центру и на узких экранах может перекрывать шапку.

### Сознательно не трогали

- панель SOS в `safety_dashboard.html`;
- заглушку SOS в `marker_terminal.html`.

Обе части ждут решения по серверному функционалу безопасности.

## Проверка перед демонстрацией

1. Поднять изолированный бэкенд и loopback-шлюз по инструкции «Быстрый запуск».
2. Открыть страницы с очисткой кэша: **Ctrl+F5**.
3. Войти под нужной ролью и проверить переадресацию.
4. Кабинет: зарегистрировать участника, оплатить, открыть QR-билет.
5. Регистратор: найти анкету, выдать карту.
6. Наборщик: сфотографировать бумажный бланк, сверить янтарные поля, сохранить анкету.
7. Маркёр: выбрать КП, отсканировать карту, проверить журнал и отправку очереди.
8. Центр управления: статистика, участники, назначение КП; под администратором — системная вкладка.
9. Проверить консоль браузера: ошибок быть не должно.
