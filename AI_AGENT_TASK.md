# План интеграции фронтенда с бэкендом (фронт пока не соответствует контрактам)

## 1. Критические различия между контрактами

### 1.1. Базовый URL и версии
| Параметр | Старый фронт | Новый бэк |
|----------|--------------|-----------|
| Base URL | `/api/` | `/api/v1/` |
| Аутентификация | Отсутствует | JWT Bearer token (`Authorization: Bearer <token>`) |
| Роли | Нет | 6 ролей: `user`, `typist`, `registrar`, `marker`, `organizer`, `admin` |

**Важно**: `participant` — это НЕ роль. Участник мероприятия — это запись в таблице `participants`, принадлежащая пользователю (`user`).

### 1.2. Концептуальные изменения

| Концепция | Старый фронт | Новый бэк |
|-----------|--------------|-----------|
| Заказ/семья | `order_id` (семейный заказ) | Отсутствует. Каждый участник регистрируется отдельно, привязан к `user_id` |
| Карта | `card_id` с префиксом дистанции (`CARD-33-XXXXX`) | `barcode` (просто строка), дистанция определяется через маршрут |
| Дистанция | Строка `"33 км"` | `route_id` (ссылка на маршрут с `name`, `distance`, `year`) |
| Анкета | `form_id` / `id` | `form_id` (уникальный номер анкеты) |

## 2. Маппинг эндпоинтов

### 2.1. Полностью совместимые (требуют только обновления URL и авторизации)

| Старый | Новый | Изменения |
|--------|-------|-----------|
| `POST /api/scans/batch` | `POST /api/v1/scans/batch` | + JWT токен, изменить структуру запроса (см. ниже) |
| `GET /api/participants` | `GET /api/v1/organizer/participants` | + JWT токен, роль `organizer`/`admin`, добавить пагинацию |

### 2.2. Требуют адаптации логики

| Старый | Новый | Что изменить |
|--------|-------|--------------|
| `POST /api/register` | `POST /api/v1/participants/register` (онлайн) + `POST /api/v1/typist/paper-form` (бумажная) | Разделить на два потока: онлайн-регистрация (из ЛК) и бумажная анкета (от наборщика). Убрать концепцию `order_id` |
| `GET /api/participants/{lookup_id}` | `GET /api/v1/participants/{id}` + `GET /api/v1/registrar/search` | Заменить "умный поиск" на два отдельных эндпоинта: поиск по ID и поиск через `registrar/search` |
| `POST /api/registrar/mark-paid` | `POST /api/v1/participants/{id}/pay` | Изменить структуру запроса (нет `lookup_id`, только `participant_id`) |
| `POST /api/registrar/issue-card` | `POST /api/v1/typist/match` | Семантика другая: `match` связывает `barcode` с `form_id`, а не привязывает карту к участнику напрямую |

### 2.3. Отсутствуют в новом бэке (требуют реализации или удаления)

| Эндпоинт | Назначение | Рекомендация |
|----------|------------|--------------|
| `POST /api/safety/emergency` | SOS-сигнал от маркёра | **Реализовать в бэке** или удалить из фронта |
| `GET /api/safety/alerts` | Сводка для штаба безопасности | **Реализовать в бэке** или удалить из фронта |
| `POST /api/ocr/recognize` | Распознавание бумажной анкеты | **Реализовать в бэке** или заменить на ручной ввод |
| `POST /api/system/reset-db` | Сброс демо-данных | Опционально, можно не реализовывать |

## 3. Пошаговый план миграции

### Этап 1: Инфраструктура (1-2 дня)

1. **Обновить `api_config.js`**
   - Изменить `DEFAULT_API_BASE_URL` на `/api/v1`
   - Добавить функцию `getAuthToken()` для получения JWT из `localStorage`
   - Добавить функцию `apiRequest(path, options)` с автоматическим добавлением заголовка `Authorization: Bearer <token>`

2. **Добавить систему авторизации**
   - Создать страницу логина (`login.html`)
   - Реализовать вызовы `POST /api/v1/auth/register` и `POST /api/v1/auth/login`
   - Сохранять токен в `localStorage`
   - Добавить проверку токена перед каждым запросом

3. **Обновить навигацию**
   - Разделить интерфейс по ролям:
     - `user` → Личный кабинет (`user_cabinet.html`)
     - `typist` → Станция наборщика (`typist_station.html`)
     - `registrar` → Терминал регистратора (`registrar_terminal.html`)
     - `marker` → Терминал маркёра (`marker_terminal.html`)
     - `organizer` → Панель организатора (новая страница)
     - `admin` → Админ-панель (новая страница)

### Этап 2: Регистрация и оплата (2-3 дня)

1. **Онлайн-регистрация (`user_cabinet.html`)**
   - Заменить `POST /api/register` на `POST /api/v1/participants/register`
   - Убрать концепцию `order_id` и семейных заказов
   - Каждый участник регистрируется отдельно
   - Структура запроса:
     ```json
     {
       "participants": [
         {
           "surname": "...",
           "name": "...",
           "route_id": 1,
           "date_of_birth": "1990-01-01",
           "gender": "male",
           "email": "...",
           "phone_number": "..."
         }
       ]
     }
     ```

2. **Оплата**
   - Заменить `POST /api/registrar/mark-paid` на `POST /api/v1/participants/{id}/pay`
   - Структура запроса:
     ```json
     {
       "payment_method": "card"
     }
     ```

3. **Просмотр своих участников**
   - Добавить вызов `GET /api/v1/participants/my` для отображения списка зарегистрированных участников

### Этап 3: Старт и выдача карт (2-3 дня)

1. **Терминал регистратора (`registrar_terminal.html`)**
   - Заменить `GET /api/participants/{lookup_id}` на:
     - `GET /api/v1/registrar/search?query=...` для поиска
     - `GET /api/v1/participants/{id}` для получения деталей
   - Заменить `POST /api/registrar/issue-card` на `POST /api/v1/typist/match`
   - Структура запроса:
     ```json
     {
       "barcode": "STK-001",
       "form_id": "MP2026-123456"
     }
     ```
   - Убрать проверку префиксов карт (`CARD-33-`, `CARD-17-` и т.д.) — теперь `barcode` не содержит информации о дистанции

2. **Поиск анкет**
   - Реализовать поиск через `GET /api/v1/registrar/search?query=...&route_id=...`
   - Поддержать поиск по `form_id`, ФИО, телефону, email

### Этап 4: Сканирование на КП (1-2 дня)

1. **Терминал маркёра (`marker_terminal.html`)**
   - Обновить `POST /api/v1/scans/batch`
   - Структура запроса:
     ```json
     {
       "checkpoint_id": 5,
       "scans": [
         {
           "barcode": "STK-001",
           "timestamp": "2026-05-15T14:15:02Z"
         }
       ]
     }
     ```
   - Добавить вызов `GET /api/v1/marker/checkpoints` для получения списка назначенных КП

### Этап 5: Админ-панель и статистика (2-3 дня)

1. **Создать новую страницу `organizer_dashboard.html`**
   - Реализовать вызов `GET /api/v1/organizer/stats` для статистики
   - Реализовать `GET /api/v1/organizer/participants` для списка участников
   - Реализовать управление маркёрами: `GET /api/v1/organizer/markers`, `PUT /api/v1/organizer/markers/{id}/assignments`

2. **Создать страницу `admin_panel.html`**
   - Управление маршрутами: `POST /api/v1/admin/routes`, `PUT /api/v1/admin/routes/{id}`, `DELETE /api/v1/admin/routes/{id}`
   - Управление КП: `POST /api/v1/admin/checkpoints`, `POST /api/v1/admin/checkpoints/batch`
   - Управление картами: `POST /api/v1/admin/maps`, `POST /api/v1/admin/maps/batch`
   - Управление пользователями: `GET /api/v1/admin/users`, `PATCH /api/v1/admin/users/{id}/role`

### Этап 6: Недостающий функционал (решение с командой)

1. **SOS и безопасность**
   - **Вариант A**: Реализовать в бэке эндпоинты `/api/v1/safety/emergency` и `/api/v1/safety/alerts`
   - **Вариант B**: Удалить из фронта функционал SOS и дашборд безопасности

2. **OCR для бумажных анкет**
   - **Вариант A**: Реализовать `/api/v1/ocr/recognize` в бэке
   - **Вариант B**: Заменить на ручной ввод через `POST /api/v1/typist/paper-form`

3. **Сброс базы**
   - Опционально, можно не реализовывать

## 4. Структура данных — что изменилось

### 4.1. Регистрация участника

**Старый формат:**
```json
{
  "type": "family",
  "familyName": "Семья Кузнецовых",
  "payerPhone": "+7 912 648-21-90",
  "participants": [
    {
      "fio": "Кузнецов Михаил Сергеевич",
      "dist": "33",
      "route": "33 км",
      ...
    }
  ]
}
```

**Новый формат:**
```json
{
  "participants": [
    {
      "surname": "Кузнецов",
      "name": "Михаил",
      "middle_name": "Сергеевич",
      "route_id": 3,
      "date_of_birth": "1986-05-12",
      "gender": "male",
      "email": "alex@example.com",
      "phone_number": "+79126482190"
    }
  ]
}
```

### 4.2. Сканирование на КП

**Старый формат:**
```json
{
  "cp_id": "КП-1 (Шарташский бор)",
  "scans": [
    {
      "card_id": "CARD-33-01452",
      "timestamp": "14:15:02",
      "route": "33 км"
    }
  ]
}
```

**Новый формат:**
```json
{
  "checkpoint_id": 5,
  "scans": [
    {
      "barcode": "STK-001",
      "timestamp": "2026-05-15T14:15:02Z"
    }
  ]
}
```

### 4.3. Выдача карты

**Старый формат:**
```json
{
  "form_id": "MP2026-849201",
  "card_id": "CARD-33-01452",
  "route": "33 км"
}
```

**Новый формат:**
```json
{
  "barcode": "STK-001",
  "form_id": "MP2026-123456"
}
```

## 5. Приоритеты и риски

### Критические (блокеры)
1. **Авторизация** — без неё не работает ни один эндпоинт
2. **Отсутствие SOS** — если это обязательный функционал, нужно реализовать в бэке
3. **Отсутствие OCR** — если наборщик критичен, нужно реализовать или заменить на ручной ввод

### Высокий приоритет
1. Регистрация и оплата
2. Выдача карт на старте
3. Сканирование на КП

### Средний приоритет
1. Админ-панель
2. Статистика для организатора

### Низкий приоритет
1. Сброс базы
2. Дашборд безопасности (если SOS не реализован)

## 6. Рекомендации для кодового агента

1. **Начать с `api_config.js`** — обновить base URL и добавить систему авторизации
2. **Создать страницу логина** — без неё невозможно тестировать остальные эндпоинты
3. **Использовать `openapi.current (1).json`** как единственный источник истины для API
4. **Игнорировать `BACKEND_INTEGRATION.md`** — он устарел
5. **Тестировать каждый эндпоинт отдельно** через Swagger UI (`/docs`) перед интеграцией с фронтом
6. **Обратиться к тимлиду** по вопросам:
   - Реализовывать ли SOS и OCR? (Ответ: будет реализовано в бэке)
   - Что делать с концепцией семейных заказов? (Ответ: пользователь просто регистрирует своих участников)
   - Нужен ли сброс базы? (Ответ: в админке можно оставить кнопку с доступом в энпдпоинт удаления)
